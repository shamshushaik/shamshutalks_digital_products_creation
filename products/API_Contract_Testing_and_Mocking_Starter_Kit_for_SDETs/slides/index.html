01 — The Problem

Backend changes break frontend tests.

WITHOUT CONTRACT

The break → the wait → the cost

Backend renames email → emailAddress without warning. Frontend tests fail. Release blocked. Team waits weeks for backend to be “ready” before UI testing can even start.

🔴 Schema drift
🔴 Type drift
🔴 Contract drift
⏳

Weeks wasted waiting for backend — while UI sits idle. No contract = no handshake.

WITH CONTRACT

Handshake before building

Contract testing is like a handshake agreement before building — both sides sign what the API will look like, so no surprises.

CONSUMER
“I need GET /users/1 → {id, name, email}”
PROVIDER
“I will return exactly that — verified by Verifier”
🤝 Pact file = contract✅ can-i-deploy gate
What is a Contract?

A written agreement between consumer (who uses the API) and provider (who builds it) about requests & responses. Like a restaurant menu: you order what’s on the menu, kitchen makes what’s on the menu.

02 — The Solution

Consumer is king — you test what your UI needs, not what backend thinks you need. Best for SDETs.

Provider publishes OpenAPI → consumer validates via openapi-validator. Best when provider has many consumers.

05 — Template Detail

Template 01 — GET /users/:id with matchers

// PactV3 — consumer-driven contract (see D2 lifecycle) import { PactV3, MatchersV3 } from '@pact-foundation/pact'; const { like, integer, string, regex } = MatchersV3; const provider = new PactV3({ dir: 'pacts', consumer: 'WebApp', provider: 'UserAPI' }); provider .given('user with id 1 exists') // provider state — seed DB .uponReceiving('a request for user 1') .withRequest({ method: 'GET', path: '/users/1' }) .willRespondWith({ status: 200, body: { id: integer(1), // any number passes — catches type drift name: string('Alice'), email: regex('^[^@]+@[^@]+\\.[^@]+$', 'alice@example.com'), active: boolean(true) } }); await provider.executeTest(async mockServer => { const res = await fetch(`${mockServer.url}/users/1`); expect(res.status).toBe(200); });
MATCHERS — WHY THEY MATTER
integer(1)Any number passes — catches string → number drift
regex(...)Enforces format — like('a@b.com') would pass not-an-email
eachLikeArray shape — catches missing/extra items
givenProvider state — tells Verifier to seed data
WHAT YOU SHOULD SEE
PASS 01-consumer-get-user.test.js ✓ returns user by id (45 ms) Pact file: pacts/WebApp-UserAPI.json → 1 interaction • spec 3.0.0
What if fails?Check dir exists → mkdir -p pacts
Rule of thumb: like for shape, regex for format, eachLike for lists. Start loose, tighten where format matters.

14 categories — catch schema drift early

Field removal🔴 BREAKING

Caught by: like / string fails
Type change🔴 BREAKING
string → number for id
Caught by: integer / string
Required field added🔴 BREAKING
New required field without default
Caught by: consumer test fails
Enum narrowing🔴 BREAKING
Remove value from allowed enum
Caught by: regex
Status code change🟡 IF CHECKED
200 → 204 or 404 → 200
Caught by: willRespondWith status
Header removal🟡 IF CHECKED
Remove Content-Type or auth header
Caught by: header matcher
Optional field added🟢 SAFE
New optional field — no contract affected
No failure — non-breaking

09 — Severity Matrix

Decision tree — is this breaking?

?Did you change the API?Start here
🔴Remove / rename a field? → Breakingfix: keep old field, version API
🔴Add required field? → Breakingfix: make optional + default
🔴Change type / enum? → Breakingfix: new field, deprecate old
🟡Change status code / header? → Breaking if checked
🟢Add optional field / endpoint? → Non-breakingsafe ✓
💡 Detection: each leaf has a Pact matcher that catches it — like for type, regex for format, willRespondWith status for codes. See PDF T7.

13 — Glossary

Key terms — analogy-first

Consumer
Who uses the API (your UI). Like a customer ordering from a menu.
Where: Pact consumer: 'WebApp'
Provider
Who builds the API (backend). Like the kitchen making the menu.
Where: provider: 'UserAPI'
Contract / Pact file
Written agreement — requests & responses. The handshake.
Where: pacts/*.json
Matcher
Flexible rule — like for type, regex for format.
Where: MatchersV3
Stub
Canned response — like a recorded voicemail, same message every time.
Tool: WireMock stubFor
Mock
Stub + verification — voicemail that also tells you who called.
Tool: WireMock verify()
WireMock mapping
JSON stub — request → response in mappings/*.json.
Where: wiremock/mappings/
Response templating
Handlebars — {{request.path}} {{now}} {{randomValue}}.
Needs response-template
Verifier
Checks real provider satisfies pacts — the CI gate.
Where: new Verifier({...})
can-i-deploy
Gate — blocks deploy if verification failed. Pact Broker feature.
Where: CI pipeline
pm.test
Postman assertion — pm.test("Status 200", () => pm.response.to.have.status(200)).
Where: Post-response tab
Breaking change
Change that breaks consumer — field removal, type change, etc. 14 categories.
Where: checklist p30
